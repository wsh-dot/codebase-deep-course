# 教学写法：从看到现象到能独立判断

## 因果链是最小教学单位

用“文件上传成功为什么还搜不到”作为教学问题，比单独列“异步队列介绍”更有效。围绕问题展开：现象 → 机制 → 数据变化 → 执行顺序 → 源码依据 → 操作 → 判读 → 迁移。

不必将每项变成固定标题，但读者应能找到答案。说明哪个字段由谁构造、在哪里保存、后面谁读取；同步返回、入队和后台执行如何关联；哪条条件导致分支跳过。用必要的因果连接句，不堆功能名。

## 深度来自中间状态

每个关键机制展示一个真实协议形状或明确标注的教学数据。可用 JSON、SQL、分数变化表、序列图或逐步手算。

例如同一证据依次变成：原文件位置 → 文本与页码 → chunk 与偏移 → 向量记录中的 chunk ID → 图谱来源 ID → 候选 → 上下文引用 → 答案出处。每步解释保留、增加、丢弃了什么。

数学不要只贴公式。先定义量，用 2–3 条数据手算，再说明计算怎样影响排序、阈值与预算。RRF 使用排名而非未经校准的不同来源原始分数；具体公式须以目标实现或可靠资料为依据。

每章至少让一个关键对象穿过两个边界。分别介绍两个函数，却不解释参数怎样交接，仍然不够完整。

## 四层阅读深度

1. 标题、目标与流程图：知道本章解决什么。
2. 默认展开的因果解释、数据例子：连续阅读可理解主线。
3. 完整代码、推导、边界条件：适当用展开面板。
4. 实验手册、源码与官方资料：供操作和深入追踪。

不要把主因果链全部藏进“了解更多”。图和正文须互相解释，例如“入队后的返回箭头表示 HTTP 已结束，Worker 仍可继续执行”。

## 段落和术语

中文段落通常 2–5 句，一个段落解决一个问题；按解释需要调整，不设视觉占屏比例。长论证按含义拆段，不能为排版截断推导。

术语首次出现给准确的一句话解释，随后落到本项目对象；浮层便于回查。类比只在有帮助时使用，马上说明实际结构和类比边界，不用比喻回避细节。

把“可提升准确度”改写为可检验条件：“新增关系对应的原文进入候选并支持答案时，才可能改善这道题；错误实体匹配也会增加噪声。”

避免“这是关键”“它非常强大”“理解即可掌握”。写具体判断：“如果最终 messages 中没有规则 R，模型本轮没读到它；先检查重排和截断。”

## 源码讲解的粒度

先给调用地图，再读函数。保留真实标识符供搜索。

| 对象 | 要解释的问题 |
|---|---|
| 参数 | 谁构造、有哪些字段、示例值是什么 |
| 状态 | 在哪一步改变、后面谁读取 |
| 调用 | 配置怎样连接接口与具体实现 |
| 条件 | 本次执行或跳过哪个分支 |
| 返回 | 调用者得到什么、能判断什么 |
| 异常 | 传递、重试、记录还是降级 |
| 副作用 | 哪个文件或库发生实际变化 |

不要把 `if` 翻成“如果”、`return` 翻成“返回”就算精读。长函数分阶段，用同一输入串起来；完整最小函数让读者最终看见连接方式。

## 实验必须有判读

操作单元写清：前提和目录 → 命令/动作 → 预期字段或界面 → 正确解释 → 失败后的下一步。区分配置文件内容与终端命令，区分宿主机、容器和远程地址。

“运行后看到成功”不合格；“输出 source、page、text，page 对应样例第二页”才可核对。除非输入、参数、算法固定，不承诺固定 chunk 数量。

## 练习考迁移，不考背诵

每章通常 3–5 道应用题，加 1–3 道手算或追踪练习。按真实误区设计干扰项，解释为什么正确、其他选择为什么不足；不只给答案字母。

优先考：证据在哪步丢失、哪种失败可降级、版本如何影响索引、哪个指标不足以证明改进、下一步最小验证是什么。不要只考缩写、文件名、语法或抄定义。

## 避免后半课程变薄

逐章检查前置概念、因果、数据、代码、操作、失败、练习七项。高级章节也须展开；先补缺失维度，再看字数。重复文字、长代码、术语表不计入解释深度。
